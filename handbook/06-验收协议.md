# 验收协议（总指挥官专用）

## 一、每次验收的机械清单（先跑这张表；2026-10-18 由「必须收到这两样」改成表）

**逐项记录事实与证据引用；命令类看退出码，不看有没有输出。** 下表用于学习验收，不把外部维护记成学员学习。纯文档改动核对引用和结构；涉及代码/入口时执行第 4–6 项，确实不适用的注明理由，不能空着。

| # | 动作 | 通过标准 | 不过怎么办 |
|---|---|---|---|
| 1 | 日报第 0 段的时间与三行 | 三行为学员原话；时间有依据，不能还原的写「未记录」并说明，不猜数值 | 三行未交 → 待补证；不代写、不重做已通过功能 |
| 2 | 当前任务逐项对照 | 完成 / 未完成及范围明确，区分功能、讲回和独立完成证据；注明实际贡献归属 | 功能失败或讲回未过 → 对应小块不通过；尚未核实 → 待补证 |
| 3 | 验证版本与提交推送 | 日报记实际提交和 push 状态；验收记录绑定已检查版本，未提交修改明确列出；通过后版本引用写入 07 | 本轮版本不明或应交未交 → 待补证；历史记录缺 hash 不等于当时未检查 |
| 4 | `uvx ruff check .` | exit 0 | 本轮引入 → 不通过；历史错误说明来源及是否阻塞；未运行 → 待补证 |
| 5 | `uvx ruff format --check <改动的目录>` | exit 0；成功也有输出 | 同第 4 项，不以输出是否为空判定 |
| 6 | `uvx pyright --pythonpath .venv/Scripts/python.exe <改动的目录>` | exit 0 | 同第 4 项；不省略解释器路径 |
| 7 | **交接发布**：按下方顺序更新 07 状态区与当前任务 | 结论和版本引用已保存，任务包与正文匹配，最后发布下一轮；「更新于」记实际日期 | 未完成发布 → 本次交接未结束，不放行新任务 |

**判定顺序：先检查已证实的失败，再检查必要证据，最后才能通过。**

| 判定 | 条件 |
|---|---|
| **不通过** | 本轮功能失败、讲回未过，或有本轮引入的检查错误。只处理对应小块，保留已成立的其他证据 |
| **待补证（收口未完成）** | 必要检查未运行、结果未取得、三行未交或本轮验证版本不明。不能当作「通过附挂账」 |
| **通过** | 本轮功能与能力要求已验证，必要检查和材料齐全。仅有明确非阻塞的历史遗留可写「通过（附挂账）」；说明来源、理由和负责轮次 |

第 7 项不是给学员判分。**验收结论已成立与下一轮已发布是两件事。** 缺材料时提醒补交；学员决定收工则如实留待补，不强迫当天补完、不倒改历史验收，也不虚填时间。

**实测锚点（2026-10-18 在本仓库跑）**：
- `uvx ruff format --check projects/rag-kb` → `51 files already formatted`，exit 0；不合格时 → `1 file would be reformatted`，exit 1。**有输出 ≠ 失败。**
- `uvx pyright projects/rag-kb`（**漏了 `--pythonpath`**）→ `23 errors`，exit 1，全是 `openai` / `dotenv` 解析不到的误报（uvx 临时环境里没有 `.venv` 的包）；带上参数 → `0 errors`，exit 0。
- `uv run ruff --version` → `Failed to spawn: ruff`（program not found）—— **一律用 `uvx`**。
- **为什么明确材料槽位**：10-17、10-18 日报记三行未写，验收行未绑定提交。它们是现存记录缺口；保留已有功能验收，不因结构整理追溯改判。历史命令输出只是当时标定，不把文件数量或固定输出措辞当通过条件。

其余证据（`progress.md` 台账行、`logs/` 日报、`notes/`）**由子教练代笔**，总指挥直接读文件。

**不要要求学员重打已答过的内容**：讲回答过一次就够了，重复敲字是纯浪费 —— 2026-09-19 学员明确抗议过「做完敲半天、验收敲半天、还要再敲笔记」。

**证据优先**：学员说"跑通了"不算数。总指挥要自己读文件、读 `git log`、读目录，再下结论。

**静态检查为什么要跑三个，不是一个**（2026-09-23 加；命令以上表第 4–6 项为准）：
原因：**`ruff check` 不报排版问题** —— `week03/hello_api.py`（09-22）和 `week04/chat_cli/main.py:12`（09-23）连续两天都有行尾空格漏过收口，就是因为只跑了 `ruff check`。**`ruff format --check` 才是抓行尾空格的。**
（`pyright` 不带 `--pythonpath .venv/Scripts/python.exe` 还会去解析 `weekNN/reference/` 的参考答案报假错 —— 09-23 实测。）

**对照测试的局限（2026-09-19 血泪教训）**：**「新旧 diff 完全一致」只能证明没退化，不能证明没缺陷** —— 老版本有同样的毛病时，两个错的东西对比也是「一致」。
涉及交互程序退出和保存时，破坏性输入须覆盖相关退出路径；这不是所有 RAG/文档任务都要重跑通讯录的要求。历史案例：09-18 的 13 项输入全部以 `quit` 结尾，漏掉了 EOF 退出丢数据。

### 验收与开工必须串行，不许并行（2026-10-14 加，学员发现流程 bug）

**问题**（2026-10-14 实测）：总指挥 13:03–13:16 还在**验收 10-13 + 重写 07**，学员 13:03 已经「开工」、子教练 13:0x 已按 07 派单 —— **三方同时动**，子教练读到的是**正在被改的 07**，且当时的坐标（`ROADMAP` 六，2026-10-18 已停写）**尚未标记 10-13 验收结果**。

**根因**：**「验收」和「开工」之间没有闸门。** 验收的收尾动作（重写 07 + 更新 07 状态区、台账落盘）**本身要花时间**，这段窗口里学员若已开工，子教练会拿到半成品状态。

**发布与中断恢复（按顺序执行）**：

| # | 规则 |
|---|---|
| 1 | 开始验收/重写派单前，将 07「下一轮是否已发布」记为「否」，保留当前任务包、上次已验版本和证据引用；此时不放行新任务。 |
| 2 | 在对应日报末追加正式结论、任务范围、实际核验版本和待补项。历史证据有效就引用，不因恢复会话再跑整格。 |
| 3 | 在 `progress.md` 记简短验收索引与证据链接；准备完整的下一任务包，逐条核实前提和既有完成项。未通过的项准确顺延，不伪装通过。 |
| 4 | 上述记录保存后，一次写入完整的 07（状态区、任务包、挂账、证据引用），最后把发布标记设为「是」。回读检查匹配后再告知可开工；写到正文不等于已经发布。 |
| 5 | 中断后若发布仍为「否」，先核对当前任务包对应的日报结论：已有正式结论就补交接，尚未验完只补未核项。若已发布则从当前派单/执行日志恢复，不重新派做已交付内容。 |
| 6 | 子教练开工/继续同一任务的读取与自检，见 `.hermes.md` §1；同日也检查任务包和结论，不只比较日期。 |

**为什么重要**：07 是「唯一派单入口」，它一旦在被改，**所有下游（子教练、学员）都在读一个移动靶**。串行一次的成本是几分钟，并行的成本是整轮返工。

**验收后更新当前派单**：按上述发布顺序重写 `handbook/07-当前任务指令.md`。尚未形成下一轮时保持未发布，并说明缺口。
原因：`.hermes.md` 启动协议第 3 条写着「`handbook/07` 存在就以它为准」，优先级高于默认流程。若不重写，子教练下次开工会把**已完成的旧任务**再派一遍（2026-09-18 实际发生过：07 里还写着「拆三层」，而三层前一天已拆完）。

### 重写 07 的强制动作：**逐项对齐排期表的「内容」列**

**规则**：`ROADMAP.md` 排期表每格有 **4 列** —— 阶段 / **内容（要学什么）** / 交付物 / 验收标准。**重写 07 时必须打开那一行，把「内容」列的每一项逐条落到 07 里，派完在 07 里列一个「本格内容清单 → 对应第几件」的对照表。**

**为什么**（2026-09-22 实例）：W4 的「内容」列 = 多轮上下文管理 / 历史裁剪 / argparse / 日志。当天 07 只派了「流式 / 四命令 / token 累计」—— 那三项在排期表里属于**「验收标准」列和交付物**，不是内容列。结果学员干满 6.5h（超 4h 预算）、把验收标准和交付物全做完了，**「内容」列却有 3 项没碰**，晚上才发现 → 学员当场质疑「一开始太少现在反而太多」。**根因是派单只挑好写的派，漏了内容列 —— 不是任务量真的超了（W4 实际约 9.5h，只有 20h/格平均预算的一半）。**

**自查口令**：派完 07，把 `ROADMAP` 那一行的「内容」列**逐项念一遍**，每一项都能在 07 里指到具体某一件 → 才算派完。**指不到的项，要么补进 07，要么明确写「顺延到 W几」并说明理由。**

### 重写 07 的第二个强制动作：**每条任务的前提必须当场核实**（2026-09-22 学员复盘）

**现象**：07 收口第 4 条写着「删掉 `llm.py` docstring 的 TODO」，但该 TODO 当晚收尾时已删（全文件 `grep TODO` = **0 处**）。学员照单执行会扑空。**同类问题已犯 2 次** —— 15:00 版 07 就含 2 条陈旧任务（会让学员找不存在的行号）。

**根因**：**07 是重写时刻的静态快照，任务状态是动态的。** 会话后半程修复文件时 TODO 已被删掉，07 没有同步销项。原有规则「说行号前先读那一行」只管**行号**，管不到**「这条任务还需不需要做」**。

**三条固定动作**：

| # | 规则 | 怎么做 |
|---|---|---|
| 1 | **派单前逐条核实现状** | 「删 X」先 `grep X`（**>0 处才许派**）；「写 Y」先确认 Y 不存在；「改 Z 第 N 行」先读第 N 行。**前提不成立的任务不许上单。** |
| 2 | **完成即销项** | 会话中任何任务完成（**无论谁做的**），**当轮**就把 07 对应条目标 ✅ 并附证据（commit hash / grep 输出），**不留到次日**。**执行主体 = 总指挥**（子教练只写日报「卡点」段，不动 07）。 |
| 3 | **收工提交前回读 07** | 全文重读，逐条对照 `git log` 与 grep 现状；已完成的当场核销，格式：`~~原文~~ —— 已核销：<证据>`。**执行主体 = 总指挥。** |

**核销格式范例**（2026-09-22 收口第 4 条，学员亲自改的，可直接照抄）：

```
4. ~~删掉 `llm.py` docstring 里那句「TODO: 你自己填这一行」~~ —— **已核销**：2026-09-22 晚全文件 grep 实测 TODO 为 0（当晚收尾时已删），本条**无需操作**，列在这里只为对账
```

**为什么用删除线而不是直接删掉条目**：直接删掉会让「这条派过吗、做了吗」失去痕迹；删除线 + 证据既销项又留账，**次日会话能看出「派过、已完成」**，不会重派。

## 二、阶段验收（每个阶段结束时问，不看代码回答）

### 阶段① Python 基础
- `contacts` 这个变量是什么类型？里面每个元素是什么？
- `line.split()` 和 `line.split(" ")` 有什么区别？

- 为什么写完 `add` 之后列表里就有数据了？哪个函数动的手？
- 如果把 `try/except` 删掉，`add 张三`（少参数）会发生什么？

### 阶段② 大模型 API、Prompt 与最小后端（W3-W8）
- `messages` 里 system / user / assistant 三种角色分别干嘛？
- `temperature` 调高调低有什么效果？什么时候该调低？

- 这次对话大概花了多少钱？怎么算出来的？
- 让模型稳定输出 JSON，你会怎么做？
- 接口（API）和你之前写的函数，区别在哪？
- 浏览器发一个请求到后端，中间经过了什么？
- 少样本提示为什么有用？什么场景下没用？

### 阶段③ RAG（核心，问得最狠）
- 一份 PDF 从上传到能被问答，中间经历了哪几步？

- 为什么选 Chroma？如果文档量涨到 100 万份，你会换什么？

- 模型是怎么"决定"调用哪个工具的？它真的在执行吗？
- Agent 死循环了怎么办？你怎么检测和终止？
- 什么时候**不该**用 Agent？（答不出说明没懂）

### 阶段⑤ 工程化与求职
- 你的项目跑一次要花多少钱？并发 10 个人会怎样？
- 服务部署在哪？挂了怎么看日志？
- 你这个项目最难的技术点是什么？（要能讲 2 分钟）

**修复必须覆盖全部退出路径**（2026-09-19 补充）：修了 `EOFError` 不等于修了「意外退出」——
`KeyboardInterrupt`（Ctrl+C）同样会跳出 `main()`，`finally` 之外的存盘代码不会执行。
**验收「退出时保存」这类需求，必须逐条跑：正常 `quit` / 输入结束（管道）/ Ctrl+C（`KeyboardInterrupt`）/ 进程被 kill。**
实测：`cli.py` 的 `except EOFError` 分支修好了前两种，`Ctrl+C` 仍然丢数据（用假 `input()` 抛 `KeyboardInterrupt` 复现，数据文件未生成）。

## 三、判定规则
- **讲不出来 = 不通过**，打回重做这一小块，不往下走。往下走只会越来越空。
- 能讲出来但在代码上写不出 → 只算"读懂了"，记录在案，下一阶段要专门安排一次手写练习。
- 通过的标准不是"完美"，是"能用自己的话讲通 + 有关键代码是自己写的"。
- **隔天独立变体**（细则见 `.hermes.md` 5·3）：只给需求与验收条件、**不给同题解法**；提示程度如实记录；15-30 分钟是**观察预算**，不是通过时限。

## 五、每周子教练合规审计（总指挥做，10 分钟）

**为什么需要**：子教练的 **7 条红线**目前靠学员上报来监督，但学员的判别力是逐周长出来的 —— 他能发现「我不知道在学什么」（感受层面），发现不了「任务粒度拆错了」「这个概念的讲法有误导」（教学层面）。而且 W1 的问题恰恰是靠学员愤怒才发现的，**愤怒是滞后信号**。

**做法**：每周日总指挥用 session_search 抽一份本周的子教练会话，对 7 条红线逐条核，把结论写进 `progress.md`：

| 红线 | 怎么核 |
|---|---|
| 1. 只给任务不说「在哪一格、以后用在哪」 | 翻会话，找第一个任务的开头两句 |
| 2. 抄完就往下走，没有讲回 | 找「讲回」环节是否存在，学员是否真的用自己的话讲过 |
| 3. 任务量配错（过少或过多） | 看**单个学习日**的任务数：**>3 件**违规（一次甩一周的量）；**<2 件**同样违规（量偏少）。正确区间见 `.hermes.md` 硬规则 3：**2-3 件 / 3-4 小时**；**提前收工不按小时机械判定**（证据弱 → 补深度；证据强且持续提前完成 → 再结合精力与意愿评估加量） |
| 4. 直接重写整个文件 | 看它给的改动是「行号 + 两处」还是「完整文件」 |
| 5. 让学员背一次性命令 / 引入阶段外技术 | 看有没有出现 `git remote add` 这类要求，或类继承/装饰器。**`async/await` 不算违规** —— `ROADMAP.md` W3 起要求教（W6 用在 FastAPI），阶段① 内不引入即可（2026-09-22 修：此前本条与 ROADMAP 打架，会把合规教学判成违规） |
| **6. 让他推导没学过的 API（先讲后练）** | 看给的骨架/任务里有没有他没学过的库或函数（`load_dotenv`、`httpx.get`、`enumerate`…），而**前面没有「这是什么 + 最小可抄样例」的讲解**。**这是 2026-09-20 新增的红线** —— 已犯 2 次（09-18 `json.loads`/`Path`、09-20 `load_dotenv`/`os.getenv`） |
| **7. 动总指挥的文件** | ⚠️ **git 层无法判定署名** —— 全部提交的 author 都是同一个 `OHCJ099`，所以「看署名」这条**给不出结论**（2026-09-22 实测，`progress.md` 亦已记载该盲区）。**可执行的替代判据**：① `git log --since=<本周> --name-only -- handbook/ ROADMAP.md .hermes.md docs/` 列出本周所有改动；② 逐条读 commit message 与改动内容，**判断「这个改动像不像子教练该做的」**（子教练只该写 `progress.md` 台账行、`logs/` 日报、`notes/`、`weekNN/` 代码与 README）；③ 有疑问时查会话库 `session_search`。**判据是「改动内容是否符合该角色职责」，不是署名。**（2026-09-22 已发生 1 次：某子会话重写 07 并提交 `415c547` —— 该次确实是越权。**注意反向的坑**：同日 6 份 handbook 的复制标记被删，总指挥一度当成「未授权改动」还原，事后学员说明**那是他让子教练修的** —— **判越权前先问学员，别只看 diff 像不像**） |
